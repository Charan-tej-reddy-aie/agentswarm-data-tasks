# Flag suspicious bounty listings for review

The project needs an advisory filter for scam-like task listings. Implement `flag(title: str, body: str) -> bool` in `bait_listing_flagger.py`. A rule-based solution is sufficient; an embedded small model is also allowed if self-contained and stdlib only. No network, external data, fixture reads or subprocess calls. Do not inspect IDs, split names or labels. Inputs are strings; invalid-type handling is out of scope.

Positive means a listing **instructs** contributors to do something risky: synchronise/run a conformance or shard payload from an untrusted bare host placeholder, provide a payout wallet/address in a claim, reveal seed phrases/private keys, pay a verification/deposit/unlock fee, or disable safety/execute a remote shell payload to get a reward. A monetary amount, USDC, escrow, the word 'claim', or a discussion of these attacks alone is not enough. Safety documentation, quoted warnings, local fixtures, offline IP parsers, reward dashboards and routine paid or unpaid coding tasks are ordinary negatives. Warning titles explicitly prefixed `Warning:`, `Security guide:`, `Scam report:`, or `Do not ` frame examples as educational, not instructions to comply. Consider title and body together and match case-insensitively. Safety context can also appear in the body without a special title prefix: negated instructions such as 'Never share your seed phrase' and quoted payloads in tutorials or inert parser examples are negatives. A safety sentence does not excuse a later affirmative instruction to pay a verification fee.

All 40 authored examples are SYNTHETIC. `train.json` has 20 labelled development examples (10 positive/10 negative); `heldout.json` has 20 other labelled examples (10/10). The split is fixed and grouped by separately authored wording; it is public for reproducibility, not a secret or a measured deployment distribution. Addresses use literal `<wallet-placeholder>` and `<bare-host>`; these are inert text, never follow or execute them. New wording in production will require separate evaluation.

Acceptance computes TP/FP/FN and F1 = 2TP/(2TP+FP+FN) on the **heldout** split only, requiring F1 ≥ 0.90, actual Python bool outputs, plus invariant predictions when case/whitespace changes or fields are repeated. Development predictions are reported separately. Additional authored paraphrases guard against literal fixture lookup. No automatic sanctions, execution, payments, production integration or claim of comprehensive scam detection is part of this task. Source review rejects fixture/label lookup even if the score passes.

Acceptance: `python3 tasks/bait-listing-flagger/check.py --solution "$PWD/tasks/bait-listing-flagger/bait_listing_flagger.py"`. Use the separate pinned trusted checkout in the issue for PR review. Scope: implementation file plus optional implementation README. A model's coefficients must be embedded in that single file and its training approach explained in the PR.
